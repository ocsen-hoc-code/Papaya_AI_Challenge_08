# T09: TransformersBackend (CUDA 4-bit / CPU)

## Description
`Qwen/Qwen3-VL-8B-Instruct`: bitsandbytes NF4 on CUDA, bf16 on CPU. Same interface and the same single-thread executor. Test the CPU path with `Qwen/Qwen3-VL-2B-Instruct`, because this 18 GB machine can't hold 8B in bf16.

## Acceptance criteria
- [x] The CPU path runs with the 2B model on this machine
- [ ] The CUDA path has mocked unit tests (done), and the README states it hasn't been run on a real GPU (README not yet updated; coordinator to do)

## Files
- `src/medextract/vlm/transformers_backend.py`

## Notes
- Transformers 5.20.2 with torch 2.14.1 (CPU wheel, installed via `.[cpu,mlx,dev]`). The class that worked is `transformers.Qwen3VLForConditionalGeneration` (`AutoModelForImageTextToText` maps `qwen3_vl` to the same class and is the fallback). `AutoProcessor` loads the processor.
- CPU dtype: bf16, chosen after a small probe matmul. Float32 is the fallback when bf16 is not supported. The kwarg is `dtype=` (transformers 5 name), not `torch_dtype`.
- Real CPU run, `Qwen/Qwen3-VL-2B-Instruct` (4.0 GB download, cached): load 3.3–4.3 s after the download. On a 640x320 receipt-like image with a 218-token prompt and 32 new tokens, decode ran at about 2.6–2.8 tok/s. Output was accurate (`RECEIPT Bangkok Hospital ...`). Mean token logprob was -0.017. The slow test (tiny image, "HELLO 42") returned `HELLO 42`.
- `tests/test_transformers_backend.py`: 16 unit tests with fake processor/model/config classes, no download (about 1 s). Covered: message building, decoding of new tokens only, logprobs (including the fallback when the model cannot report them), 4-bit NF4 requested on CUDA, bf16 with no quantization on CPU, load failures wrapped in `VLMError`, and close releasing the model. The class lookups go through module-level helpers, because patching attributes on the lazily loaded `transformers` package did not reliably take effect.
- CUDA path: mocked tests only. It has NOT been run on a real GPU. The README still needs to say this (README is not in this task's files).
- `output_scores=True` keeps one vocab-sized score tensor per generated token, which costs memory on long generations (about 0.6 MB per token for a 152k vocab).
